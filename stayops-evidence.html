PRODUCT / ENGINEERING EVIDENCE

StayOps

Hotel operations, built around the teams doing the work.

StayOps is an operations-first hotel team coordination platform. Current source implements daily operational queues, housekeeping and room readiness, maintenance incidents, shift handovers, inventory/supplies, linen movements and related workflows. Reservation records are retained as context, not the product's primary purpose.

01 / CONTEXT

The problem
behind the interface.

StayOps addresses everyday hotel coordination: dirty rooms need a cleaner and an inspector; an incident may block a room; shifts must transmit requests; linen and supply movements need to be tracked. Reservations remain useful operational context, but this is not presented as a new booking engine.

Daily work queue→Assignment→Task completion→Inspection→Room readiness
02 / ARCHITECTURE

Designed around constraints.

Technology choices are explained through what they protect or enable, rather than listed as logos.

01

State, not decoration

Current operations source computes room readiness from housekeeping status, inspection evidence, occupancy context and operational blockers. It also implements daily task queues and team workflows; the published database state still needs independent validation.

TypeScript · Domain rules
02

Team coordination

Source routes include /app (Operations today), /app/housekeeping, /app/handovers, /app/supplies and /app/linen. Next.js server actions use property-scoped Supabase access. Authorization must be checked at both application and database levels.

Next.js · Supabase Auth · PostgreSQL
03

Property-local schedules

The application uses property-local dates for daily task and readiness logic. Automated tests exercise date boundaries and daylight-saving behavior; schedules and deployed database policies require separate verification.

Intl.DateTimeFormat · Node tests
03 / EVIDENCE

What can actually be checked?

No invented clients, invented numbers or imaginary certifications. Each statement has a clear verification boundary.

CLAIMAVAILABLE EVIDENCEBOUNDARY

A working public interface

The public /demo/workspace and /demo/planning routes are reachable. They show the existing sample-hotel cockpit and room planning; they are not a full interactive showcase of the merged operations-first modules.

The sample demo retains PMS-era emphasis. It cannot prove that handover, supply, linen and assignment writes work in production.

Domain behavior in source

Source reviewed in the merged main branch includes app/app/page.tsx (Operations today), app/app/handovers/page.tsx, app/app/supplies/page.tsx, app/app/linen/page.tsx and housekeeping logic. The operations platform changes were merged in PR #6.

Code existence is verified; live deployment and end-to-end operation of every new module have not been demonstrated.

Focused automated tests

On 23 October 2026, GitHub Actions ran the three test suites on a Linux runner: 57 tests passed, 0 failed; TypeScript validation and Next.js build also passed (revision 13891edc).

CI run 40002475017 is recorded in the private repository; independent public review requires repository access. No browser E2E or live database verification was performed.

Documented release risks

The private repository contains specific security, schema, migration and staging readiness reports.

Prior reports noted unresolved staging/production gates; no production security sign-off is claimed.

04 / ENGINEERING HONESTY

What is not
proven yet.

  • Production database policy and migration parity have not been freshly verified here.
  • Permission boundaries, atomic task transitions, tenancy separation and deployment/schema parity still require independent testing.
  • Real signed-in browser scenarios, backup restoration and field adoption require separate proof.
  • No hotel client deployment, measured efficiency improvement or completed security certification is claimed.

A responsible prototype is explicit about the tests it passes and the production checks it has not passed.
