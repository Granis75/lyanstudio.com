01 / CONTEXT

The problem
behind the interface.

Hospitality teams cannot decide whether a room is available by looking at a single status field. A reservation, ongoing cleaning, technical room block or unresolved incident may change the actual answer. StayOps models this decision across connected workflows.

Reservation→Check-in→Check-out→Cleaning→Inspection→Ready
02 / ARCHITECTURE

Designed around constraints.

Technology choices are explained through what they protect or enable, rather than listed as logos.

01

State, not decoration

A room is marked arrival-ready only after checking occupancy, maintenance blocks, critical incidents, unfinished tasks and explicit inspection evidence.

TypeScript · Domain rules
02

Role-aware operations

Authenticated workflows live in Next.js server actions using a property-scoped Supabase client. Role checks and database policies must both agree.

Next.js · Supabase Auth · PostgreSQL
03

Property-local time

Readiness calculations follow a property's timezone. Tests include midnight boundaries and the daylight-saving change in Paris.

Intl.DateTimeFormat · Node tests

04 / ENGINEERING HONESTY

What is not
proven yet.

  • Production database policy and migration parity have not been freshly verified here.
  • Concurrent reservations need database-level conflict testing, not only application pre-checks.
  • Real signed-in browser scenarios, backup restoration and field adoption require separate proof.
  • No hotel client metrics, real revenue improvement or production PMS certification are claimed.

A responsible prototype is explicit about the tests it passes and the production checks it has not passed.
