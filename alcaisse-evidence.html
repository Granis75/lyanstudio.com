WINDOWS POINT OF SALE

AlCaisse

Retail checkout designed to work even when the internet does not.

A client-developed Windows checkout application bringing together product and barcode lookup, basket and payment handling, cash sessions, inventory control, receipts and daily reporting. Local SQLite persistence supports the offline-first design.

01 / CONTEXT

The problem
behind the interface.

A retailer needs checkout, stock and cash-session records to remain consistent, even without reliable connectivity. AlCaisse is designed around locally stored transactions and recovery procedures rather than a remote checkout API.

Cash session→Barcode→SQLite sale→Stock movement→Receipt→Close session

03 / HOW IT WORKS

Built for the Windows counter.

AlCaisse is built with Electron, React, TypeScript and SQLite. Sales, inventory updates and cash-session records are stored locally, so the checkout workflow is designed to continue without an internet connection.

The desktop project also includes receipt-printing adapters and local backup tools. Printer and cash-drawer compatibility depends on the physical equipment and has not been independently validated.

A packaged Windows version has been inspected and tested locally by the developer. The executable belongs to a private client project and is not distributed on this website.

04 / ARCHITECTURE

Engineering behind the counter.

Technology decisions address consistency, desktop isolation and recovery.

01

Desktop boundary

The React interface uses typed Electron IPC. Database and device operations are placed in the main process; Node integration is disabled in the renderer.

Electron · React · TypeScript
02

Transactional local data

SQLite models cash sessions, sales, stock decrements, cancellations and corrections. An executable critical-path smoke scenario exercises key areas.

SQLite · Local persistence
03

Devices and recovery

Receipt output includes a test-to-file path and printer adapters. Local backup and guarded restore are implemented; physical peripherals still require validation.

ESC/POS · Backups · Windows
05 / VERIFICATION NOTES · OCT 2026

Evidence and its limits.

This is developer-reported client work for an unnamed client. The evidence below separates inspected artifacts and private test results from claims not independently established.

01

Windows package inspected

A supplied AlCaisse 0.1.0 executable (69,625,952 bytes) was statically identified as Windows PE32 (Intel x86) with NSIS portable packaging and AlCaisse metadata. The file remains private and unsigned.

Static inspection does not establish runtime, installation or client acceptance.
02

Desktop source and CI

The private codebase includes Electron entry, a database service, backup logic, printer adapters and renderer. On 23 October 2026, a Windows GitHub Actions runner passed scripts/smoke-critical.js against temporary SQLite data: ok=true across 17 named control areas (revision 08a87ad, run 40002483409).

Private logs; not a packaged EXE or hardware acceptance test.
03

Release and offline boundaries

A Windows packaging workflow includes native SQLite architecture checks. Earlier Windows 7 builds failed during native dependency rebuilding; a compatibility fix was still under test. Checkout persistence is designed to remain local.

Windows 7 hardware, power-loss recovery and field validation remain unverified.
06 / VALIDATION BOUNDARIES

What is not proven yet.

  • The online simulation is not the Electron/SQLite desktop executable and cannot validate printer or cash-drawer compatibility.
  • Default development PINs and legacy Windows 7 support require a separate production security review.
  • The developer reports installing and testing the application on a Windows machine, but no independent client acceptance record, peripheral test record or fiscal certification has been supplied.
  • No real-store deployment, adoption or performance improvements are claimed without supporting evidence.

A prototype is best assessed by the tests it passes and the production checks it has yet to pass.
